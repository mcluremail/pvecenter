# VirtDeck — идеи развития по результатам анализа ProxCenter

> **Статус:** идеи / backlog на будущее
> **Приоритет:** не являются текущим обязательством по реализации
> **Источник идей:** анализ возможностей ProxCenter и сравнение с архитектурой VirtDeck
> **Главный принцип:** заимствовать идеи и пользовательские сценарии, но не копировать код или реализацию.

---

## 1. Зачем существует этот документ

ProxCenter представляет собой существенно более крупную централизованную платформу управления инфраструктурой Proxmox VE. У него есть ряд интересных функций и UX-подходов, которые могут быть полезны VirtDeck.

Цель этого документа — сохранить эти идеи в виде долгосрочного банка возможностей.

**Важно:** этот документ не означает, что VirtDeck должен превращаться в ProxCenter.

Основная концепция VirtDeck остаётся:

> **Быстрый desktop-клиент для управления распределённой инфраструктурой виртуализации без обязательного центрального сервера.**

Поэтому идеи необходимо оценивать с точки зрения архитектуры и философии VirtDeck.

## 2. Что можно заимствовать

#### Идея

Более информативное представление всей инфраструктуры:


* состояние;
* загрузку CPU;

* replication status;
* tags.

#### Ценность

Особенно важно для инфраструктуры с большим количеством независимых PVE-хостов.

**Высокий.**

## 3. Глобальный поиск инфраструктуры

### Идея

Поиск должен работать не только внутри текущего кластера, а по всему подключённому окружению.

Желательный сценарий:

```text
Ctrl+K

web-prod
```

Результаты:

```text
VM 104  web-prod
Cluster: Moscow
Node: pve03
IP: 10.20.30.15
Status: running
```

Поиск должен потенциально поддерживать:

* VM;
* CT;
* node;
* cluster;
* storage;
* IP;
* hostname;
* tags;
* task;
* PBS;
* backup;
* replication.

### Важная особенность VirtDeck

По возможности поиск должен работать по локальному кэшу и не требовать сетевого запроса для отображения уже известных объектов.

### Возможное развитие

Поиск команд:

```text
> migrate VM 104
> restart VM 104
> snapshot VM 104
```

Это может стать основой command palette.

### Приоритет

**Высокий.**

**Очень высокий.**

## 7. Migration Wizard

### Идея

Сделать миграцию отдельным понятным операторским сценарием.

Пример:

```text
Перемещение VM 104

Источник:
  Moscow / pve03

Назначение:
  Moscow / pve05

✓ CPU совместим
✓ Storage доступен
✓ Network существует
✓ VM running
⚠ Target RAM utilization: 87%
```

### Важная идея

До выполнения операции VirtDeck должен объяснить:

* что будет сделано;
* какие проверки пройдены;
* какие проблемы обнаружены;
* почему операция запрещена;
* какие узлы подходят.

### Потенциальная функция

#### «Показать подходящие узлы»

VirtDeck сам вычисляет возможные destination nodes.

### Приоритет

**Высокий / средний.**

* clone;

* storage move;

* backup;
* replication;
* VM creation;
* network changes;

## 9. Bulk Operations

### Идея

Централизованное выполнение операций над несколькими объектами.

Например:

```text
Выбрано: 17 VM

[Start]
[Shutdown]
[Reboot]
[Snapshot]
[Tag]
[Move]
```

### Обязательно

Bulk Operations должны:

* показывать список объектов;
* заранее проверять возможные ошибки;
* показывать прогресс каждой операции;
* позволять продолжать после ошибки;
* не блокировать UI;
* корректно обрабатывать частичный успех.

Это особенно важно с учётом принципов M0.

### Приоритет

**Высокий.**

## 19. DRS Advisor

### Важная идея: сначала Advisor, потом автоматизация

Не пытаться сразу реализовать полноценный автоматический DRS.

Сначала сделать рекомендации:

```text
Балансировка

pve01    42%
pve02    48%
pve03    91%

Рекомендация:

VM 217
pve03 → pve01

Освободит на pve03:
  CPU: 14%
  RAM: 12 GB

[Показать детали]
```

### Почему это хороший путь

Пользователь принимает решение сам.

VirtDeck анализирует инфраструктуру, но не совершает опасных автоматических действий.

Это хорошо соответствует принципу:

> Сначала помогать оператору принимать решение, потом автоматизировать.

### Приоритет

**Долгосрочный.**

## 20. Infrastructure Analyzer

Это потенциально более фундаментальная возможность.

### Идея

Поверх существующего `DataProvider` создать слой анализа инфраструктуры.

```text
                    VirtDeck
                       │
              Infrastructure Analyzer
                       │
        ┌──────────────┼──────────────┐
        ↓              ↓              ↓
     Problems       Capacity        Safety
        │              │              │
     Backup          Node load      Migration
     failed          high           unsafe
```

### Примеры правил

```text
if backup_age > threshold:
    problem()

if node_ram > 90%:
    warning()

if target_storage_missing:
    migration_blocked()

if replication_delayed:
    warning()
```

### Важно

На первом этапе никакого ИИ не требуется.

Обычные детерминированные правила уже дадут большую пользу.

### Возможное будущее

Позже поверх Analyzer можно добавить:

* рекомендации;
* автоматические действия;
* планирование;
* прогнозирование;
* локальный ИИ-помощник.

### Приоритет

**Стратегический / долгосрочный.**

## 21. Что НЕ следует переносить из ProxCenter

Некоторые возможности ProxCenter не соответствуют текущей философии VirtDeck.

### Не превращать VirtDeck в обязательную серверную платформу

Не делать центральный сервер обязательным для базовой работы.

VirtDeck должен продолжать работать напрямую с PVE/PBS.

---

### Не вводить PostgreSQL как источник истины без необходимости

Текущая модель:

```text
PVE/PBS
   ↓
Provider
   ↓
VirtDeck cache
   ↓
UI
```

имеет важное преимущество: нет отдельного обязательного сервера.

---

### Не строить полноценный HA Control Plane

Это уже территория платформы уровня ProxCenter/vCenter.

Для VirtDeck это отдельный продуктовый уровень сложности.

---

### Не делать MSP / multi-tenant основным направлением

Это может быть интересно в будущем, но не является основной задачей VirtDeck.

---

### Не делать Enterprise RBAC/SSO/LDAP раньше времени

Подобные функции естественным образом появляются, если появляется центральный сервер.

Для desktop-клиента приоритет существенно ниже.

---

### Не делать автоматический DRS слишком рано

Автоматическое перемещение VM — потенциально опасная операция.

Сначала:

1. анализ;
2. рекомендации;
3. подтверждение;
4. ручная миграция;
5. только потом возможная автоматизация.

---

### Не превращать VirtDeck в веб-клон ProxCenter

Наличие похожих функций не означает необходимость копировать их UI или архитектуру.

Сильная сторона VirtDeck:

* desktop;
* быстрый запуск;
* локальный cache;
* offline startup;
* OS keyring;
* прямое подключение;
* быстрый отклик;
* отсутствие обязательного сервера.

Это необходимо сохранить.

## 23. Главная продуктовая идея

Не копировать ProxCenter как продукт.

Использовать его как источник идей и контрольную точку для сравнения.

### ProxCenter

Основная идея:

> **Централизованная платформа управления инфраструктурой Proxmox.**

### VirtDeck

Потенциальное позиционирование:

> **Быстрый desktop control deck для администратора виртуальной инфраструктуры.**

VirtDeck не обязан выигрывать количеством Enterprise-функций.

Его потенциальное преимущество:

> **Открыл → мгновенно увидел всю инфраструктуру → нашёл нужный объект → понял проблему → выполнил действие.**

## 24. Принцип разработки этих функций

Все будущие функции должны по возможности соответствовать уже сформированным принципам VirtDeck:

### UI не блокируется

Сетевые и дисковые операции выполняются через worker.

### Быстрый отклик

Click → visual reaction должен оставаться в пределах установленного performance budget.

### Optimistic UI там, где это безопасно

Пользователь должен видеть реакцию интерфейса до завершения долгой операции.

### Кэш используется как полноценный источник для чтения

Интерфейс не должен постоянно ждать сеть.

### Опасные операции должны быть объяснимыми

Перед выполнением показывать:

* что будет сделано;
* над каким объектом;
* какие проверки пройдены;
* какие предупреждения существуют.

### Возможность постепенного внедрения

Новые функции не должны требовать обязательного перехода к центральному серверу.

---

## 25. Важное юридическое правило

Идеи, пользовательские сценарии и функциональные концепции можно использовать как источник вдохновения.

При реализации VirtDeck:

* не копировать исходный код ProxCenter без осознанного соблюдения его лицензии;
* не переносить Enterprise-код;
* не копировать их логотипы и фирменные элементы;
* предпочитать независимую реализацию собственными средствами;
* использовать ProxCenter как reference product, а не как исходную кодовую базу.

Особенно желательно для VirtDeck:

> **«Изучили → поняли задачу → спроектировали собственное решение → реализовали с нуля».**

---

## 26. Примечание для roadmap

Этот документ **не является обязательным roadmap**.

При планировании следующих версий:

1. Не вытаскивать все пункты автоматически в текущий спринт.
2. Сначала оценивать их относительно текущего roadmap.
3. Не ломать M0/M1/M2 и уже принятые архитектурные решения ради этих идей.
4. Не добавлять функции только потому, что они есть у ProxCenter.
5. Приоритет отдавать функциям, которые усиливают уникальные преимущества VirtDeck.
